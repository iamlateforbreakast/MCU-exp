# BT/BLE linker-script section-placement patch for `esp32c3db`

**Status: written and validated with a real link, 2026-08-26.** Unlike
`../bsp-patch/` (a patch against real, hand-written RTEMS C source files),
this patches `linkcmds.base` - which, for RISC-V BSPs including
`esp32c3db`, is **generated by waf's spec-driven build system at BSP-build
time**, not a checked-in template file (confirmed: grepped the full RTEMS
`main` kernel checkout for `linkcmds*` under `bsps/riscv/` - zero hits,
unlike `bsps/arm/shared/start/linkcmds.base` etc. which do exist as real
source for other architectures). This means the exact source-level YAML/
spec input that generates it hasn't been identified yet - what's here is a
**validated post-build patch** applied to the already-built/installed
`$RTEMS_ROOT/riscv-rtems7/esp32c3db/lib/linkcmds.base`, not something that
survives an `rm -rf ~/kernel && waf configure && waf` from scratch yet.
Finding the real generator input (to make this durable across rebuilds) is
the natural next step, not attempted here.

## What this solves

Two real, confirmed gaps found by actually attempting a link of vendored
`bt.c` + the real `libbtdm_app.a` blob against this BSP (2026-08-26):

1. **`_bt_data_start`/`_bt_data_end`/`_bt_bss_start`/`_bt_bss_end`/
   `_bt_controller_data_start`/`_bt_controller_data_end`/
   `_bt_controller_bss_start`/`_bt_controller_bss_end`** - `bt.c` needs
   these 8 symbols bracketing specific object files' `.data`/`.bss`
   contributions. Confirmed via reading real IDF's own linker-fragment
   files (`components/bt/linker_common.lf`,
   `components/bt/linker_rw_bt_controller.lf`, both real Apache-2.0
   source, not vendored here - just read for their real semantics):
   - `linker_common.lf`'s `archive: libbt.a` mapping (`libbt.a` is where
     real IDF compiles `bt.c` itself into) generates `_bt_bss_start/_end`
     and `_bt_data_start/_end` around **`bt.c`'s own** `.bss`/`.data`.
   - `linker_rw_bt_controller.lf`'s `archive: libbtdm_app.a` mapping
     generates `_bt_controller_bss_start/_end` and
     `_bt_controller_data_start/_end` around **the closed blob's**
     `.bss`/`.data` - i.e. "controller" in the symbol name refers to the
     radio-controller blob specifically, not to `bt.c` (the confusing
     part that took real recon to untangle - `bt.c` is the "frontend",
     `libbtdm_app.a` is the "controller").

2. **`.iram1.*`/`.dram1.*` sections aren't handled by this BSP's linker
   script at all** - confirmed by attempting the real link before this
   patch: `IRAM_ATTR`/`DRAM_ATTR`-tagged code/data (used extensively
   across `bt.c`, `esp_phy`, `esp_gpio_reserve.c`, `hal/efuse_hal.c`, ...)
   compiles to `.iram1.N`/`.dram1.N` sections that fell into this BSP's
   `.unexpected_sections` catch-all region (a deliberate 0-length "any
   section landing here is a bug" safety net) and overflowed it by
   ~30KB. Not specific to BLE - any vendored file using these real
   ESP-IDF attribute macros hits this.

## The fix

**Deliberate simplification, not a full IRAM/DRAM port**: this BSP has no
physically separate IRAM/DRAM memory banks the way Xtensa ESP32 does (see
`linkcmds`'s `MEMORY`/`REGION_ALIAS` block - `REGION_TEXT`/
`REGION_FAST_TEXT` are both `CODE_FLASH_MAPPED`, `REGION_DATA`/
`REGION_FAST_DATA` are both the same single `RAM` region already), and
this port has no flash-cache-disable/SPI-flash-write scenario that would
require code to be physically resident in RAM while flash is
inaccessible (the actual reason real ESP-IDF cares about true IRAM
residency). So `.iram1.*` is folded into the existing `.text` output
section (same `REGION_TEXT` as everything else) and `.dram1.*` into the
existing `.data` output section - correct for this port today, flagged
here in case a future SPI-flash/deep-sleep driver ever needs to revisit
it.

### Patch to `linkcmds.base`'s `.text` output section

```diff
   .text : ALIGN_WITH_INPUT {
     bsp_section_text_begin = .;
     *(.text.unlikely .text.*_unlikely .text.unlikely.*)
     *(.text.exit .text.exit.*)
     *(.text.startup .text.startup.*)
     *(.text.hot .text.hot.*)
     *(.text .stub .text.* .gnu.linkonce.t.*)
+    *(.iram1 .iram1.*)
     /* .gnu.warning sections are handled specially by elf32.em.  */
     *(.gnu.warning)
   } > REGION_TEXT AT > REGION_TEXT_LOAD
```

### Patch to `linkcmds.base`'s `.data` output section

```diff
   .data : ALIGN_WITH_INPUT {
     bsp_section_data_begin = .;
+    _bt_data_start = .;
+    *bt.o(.data .data.* .gnu.linkonce.d.*)
+    _bt_data_end = .;
+    _bt_controller_data_start = .;
+    *libbtdm_app.a:*(.data .data.* .gnu.linkonce.d.*)
+    _bt_controller_data_end = .;
     *(.data .data.* .gnu.linkonce.d.*)
+    *(.dram1 .dram1.*)
     SORT(CONSTRUCTORS)
   } > REGION_DATA AT > REGION_DATA_LOAD
```

### Patch to `linkcmds.base`'s `.bss` output section

```diff
   .bss : ALIGN_WITH_INPUT {
     *(.dynbss)
+    _bt_bss_start = .;
+    *bt.o(.bss .bss.* .gnu.linkonce.b.*)
+    _bt_bss_end = .;
+    _bt_controller_bss_start = .;
+    *libbtdm_app.a:*(.bss .bss.* .gnu.linkonce.b.*)
+    _bt_controller_bss_end = .;
     *(.bss .bss.* .gnu.linkonce.b.*)
     *(COMMON)
     bsp_section_bss_end = .;
   } > REGION_BSS AT > REGION_BSS
```

**Why the `_bt_*`/`_bt_controller_*` markers come *before* the generic
`*(.data ...)`/`*(.bss ...)` wildcard, not after**: GNU ld places each
input section the first time any rule matches it. Putting the specific
`bt.o(...)`/`libbtdm_app.a:*(...)` rules first pulls exactly those objects'
sections out and brackets them with the `_start`/`_end` symbols; the
later generic wildcard then only sees (and correctly places) everything
*else's* `.data`/`.bss`, with no double-placement or ordering conflict.

## Validated with a real link (2026-08-26)

`riscv-rtems7-gcc` (using the real `-B<bsp-lib-dir> -qrtems` flags
`pkg-config --libs riscv-rtems7-esp32c3db.pc` produces, not raw `ld`
directly - raw `ld` doesn't know the BSP's implicit `start.o`/`linkcmds`
search paths) linking vendored `bt.o` + the real, fetched `libbtdm_app.a`
against a copy of the installed `linkcmds.base` with this patch applied,
with `-Wl,--unresolved-symbols=ignore-all` (structural test only - the
~99 other undefined symbols from `../vendor/README.md`'s "Linking"
section aren't resolved yet, this only validates the section-placement
mechanism itself) succeeded and produced real, sane, non-overlapping
addresses:

```
3fc80000 D _bt_controller_data_start
3fc80000 D _bt_data_end
3fc80000 D _bt_data_start
3fc8015e D _bt_controller_data_end
3fc80700 B _bt_bss_end
3fc80700 B _bt_bss_start
3fc80700 B _bt_controller_bss_start
3fc80a32 B _bt_controller_bss_end
```

`_bt_data_start == _bt_data_end` and `_bt_bss_start == _bt_bss_end`
(zero-length ranges) because `bt.c` itself turned out to have no
non-empty `.data`/`.bss` contribution in this build (its state lives
elsewhere, e.g. heap-allocated via `osi_funcs_t`) - a real, confirmed
result, not a bug in the fragment; the blob's own ranges
(`_bt_controller_*`) are non-empty (350 bytes of `.data`, 818 bytes of
`.bss`) as expected. Without the `.iram1.*`/`.dram1.*` fix, the link
failed first with `.unexpected_sections` overflowing by ~30KB - applying
just the `_bt_*` markers without this fix would not have been a complete,
honest validation.

## Integration steps (not yet made durable across a rebuild)

1. Build/install the `esp32c3db` BSP as usual (`../ESP32-C3-RTEMS.md`).
2. Apply the three diffs above to
   `$RTEMS_ROOT/riscv-rtems7/esp32c3db/lib/linkcmds.base` (the *installed*
   copy - this is a post-build patch, see "Status" above for why).
3. Link the application with `bt.o`/`libbtdm_app.a` on the command line as
   shown - the object/archive names in the patch (`bt.o`, `libbtdm_app.a`)
   must match exactly what's passed to the linker, since GNU ld's
   `objname(sections)`/`archive:*(sections)` syntax matches by filename.

**Not yet done**: locating the real waf/spec source that generates
`linkcmds.base`, so this survives `waf configure && waf install` without
